# Slice 2.2 — Google OAuth in the native shell

**Status:** awaiting Josh's approval
**Slice:** 2 (Capacitor shell runs on both platforms)
**Decision:** D14 (system browser plus deep link), chosen 2026-09-03
**Depends on:** the committed shell (`3028c4e`)

## What this does

Makes Google sign-in work inside the iOS shell. Today the Google button in Clerk's embedded `<SignIn />` navigates `accounts.google.com` inside WKWebView, and Google refuses embedded webviews with `disallowed_useragent`. The fix moves the Google leg out to the system browser and hands the resulting session back into the webview.

It also introduces `isNativeApp()`, which slice 7 already depends on for hiding Stripe.

## Why this shape

The hard constraint is that **cookies do not cross between the system browser and WKWebView.** Any flow that authenticates in Safari leaves the session in Safari. So the session has to be handed over explicitly, and Clerk's supported mechanism for that is a **sign-in token** exchanged with the `ticket` strategy. Both halves exist in the pinned versions: `@clerk/backend` ships `signInTokens.createSignInToken({ userId, expiresInSeconds })` and `@clerk/types` 4.26.0 declares `TicketStrategy = 'ticket'`.

Rejected alternatives are in D14. The short version: a native Google SDK avoids the browser bounce but adds a second, entirely separate path for Apple, and dropping Google inside the app locks out every user who signed up with it, since those Clerk accounts have no password.

## The flow

1. **Webview.** User taps Google on `/sign-in`. Native build only. The handler generates a random `nonce`, keeps it in memory, and opens the system browser at `https://spritzofficial.app/native-auth/start?nonce=<nonce>`.
2. **Browser.** `/native-auth/start` stores the nonce in a short-lived, httpOnly, SameSite=Lax cookie and runs Clerk's normal Google redirect flow, with the completion URL set to `/native-auth/complete`. Google sees a real Safari user agent and is satisfied.
3. **Browser.** `/native-auth/complete` is a server route. The Clerk session cookie exists here, so it reads `userId` from `auth()`, mints a sign-in token with `expiresInSeconds: 60`, reads the nonce back from the cookie, clears it, and 302s to `app.spritzofficial://sso-callback?ticket=<token>&nonce=<nonce>`.
4. **iOS.** The custom scheme wakes the app. `@capacitor/app`'s `appUrlOpen` fires in the webview.
5. **Webview.** The listener compares the returned `nonce` against the one it generated and discards the callback on any mismatch. On a match it calls `signIn.create({ strategy: 'ticket', ticket })`, then `setActive({ session: createdSessionId })`, closes the browser with `Browser.close()`, and routes to the post-sign-in destination.

### Why the nonce and the 60 seconds

The ticket travels in a URL through the OS URL router, and on iOS another installed app can in principle claim the same custom scheme. Two mitigations, both cheap: the token is single-use and expires in 60 seconds, and the webview refuses any callback whose nonce it did not issue. A hijacker gets a token it cannot pair with a waiting nonce.

`@capacitor/browser` uses `SFSafariViewController`, which routes the callback through the OS rather than delivering it privately the way `ASWebAuthenticationSession` would. That is the residual risk this design accepts, in exchange for staying on first-party Capacitor plugins. If it ever needs closing, the swap is a plugin change, not a protocol change.

## Files

**New**
- `lib/native.ts` — `isNativeApp()`, SSR-safe, reads `window.Capacitor?.isNativePlatform?.()` and returns false on the server. Exports `NATIVE_URL_SCHEME`.
- `app/native-auth/start/route.ts` — sets the nonce cookie, redirects into Clerk's Google flow.
- `app/native-auth/complete/route.ts` — mints the sign-in token, redirects to the custom scheme.
- `components/native-auth-bridge.tsx` — client, mounted once in the root layout. Registers the `appUrlOpen` listener and owns the pending nonce. Renders nothing.
- `components/native-social-buttons.tsx` — client. The Google button shown in place of Clerk's on native.

**Changed**
- `app/sign-in/[[...sign-in]]/page.tsx` and the sign-up equivalent — on native, hide Clerk's social buttons through `appearance` and render `<NativeSocialButtons />` above the form. Web is untouched.
- `app/layout.tsx` — mount `<NativeAuthBridge />`.
- `capacitor.config.ts` — nothing, the scheme lives in Info.plist.
- `ios/App/App/Info.plist` — `CFBundleURLTypes` registering `app.spritzofficial`.
- `package.json` — `@capacitor/browser`, `@capacitor/app`.

## Acceptance criteria

1. **Given** the iOS shell on a device with the app signed out, **when** the user taps Google on `/sign-in`, **then** the flow opens in the system browser, not the webview, and Google shows its normal account chooser rather than `disallowed_useragent`.
2. **Given** the browser flow completed, **when** Google returns, **then** the app comes to the foreground, the browser closes on its own, and the webview is signed in as that user.
3. **Given** a callback whose nonce does not match the pending one, **when** it arrives, **then** it is discarded and no session is created.
4. **Given** the same ticket replayed after use or after 60 seconds, **when** it is exchanged, **then** Clerk rejects it and the app shows a recoverable error rather than a blank screen.
5. **Given** the user cancels in the system browser, **when** they return to the app, **then** the sign-in page is unchanged and usable, with no spinner stuck on.
6. **Given** the web app in a desktop or mobile browser, **when** a user signs in with Google, **then** nothing about the existing flow has changed.

## Out of scope

- Sign in with Apple. It reuses this machinery and is 2.3, with its own decision about native `ASAuthorizationController` versus the same browser path.
- Android. The scheme registration and intent filter are the Android half of slice 2.
- Sign-up. The same buttons appear on `/sign-up`, but proving the new-user path is a 2.6 device task, not a code difference.
- Session persistence across app restarts, which is Clerk's own cookie behavior in the webview and is unchanged by this.

## How it will be shown working

A screen recording in the Simulator: tap Google, the browser sheet rises, account chooser, return to the app signed in. Plus the console log of the ticket exchange. Criteria 3 and 4 get a deliberate bad-nonce and replayed-ticket run. Criterion 6 gets a browser pass on the deployed preview.

## Known risk

`@clerk/nextjs` is pinned at 5.7.6, which is a 2024 line. Current Clerk docs describe `signIn.sso()`, a newer API. `authenticateWithRedirect` and the `ticket` strategy are both present in the installed types, so this design builds against what is actually there. Upgrading Clerk is not part of this slice and should not be attempted inside it.
